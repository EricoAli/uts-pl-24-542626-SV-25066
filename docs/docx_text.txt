1. Inisialisasi dan Pengujian Aplikasi Web Sederhana Berbasis Laravel
Tahap pertama dalam pelaksanaan praktikum ini adalah melanjutkan pengembangan repositori proyek dengan mengonversinya menjadi sebuah aplikasi web Laravel yang fungsional. Proyek dikembangkan menggunakan kerangka kerja Laravel 13 yang didukung oleh mesin templat Blade serta bundler aset Vite. Pada antarmuka utama, dibuat berkas view dashboard.blade.php yang dipetakan melalui rute utama web pada routes/web.php. Halaman dashboard ini menyajikan informasi kontekstual mencakup judul modul perkuliahan 'Konstruksi Evolusi Perangkat Lunak', identitas mahasiswa (Nama, NIM, dan status keaktifan), serta rincian tumpukan teknologi (technology stack) yang digunakan.
Gambar 1. Halaman antarmuka dashboard aplikasi Laravel 13 yang diakses secara lokal pada peramban web.
Setelah antarmuka aplikasi berhasil dibangun, langkah krusial berikutnya adalah melakukan verifikasi fungsionalitas dan ketahanan kode secara lokal sebelum didorong ke repositori remote. Pengujian dilakukan melalui konsol perkakas bawaan Laravel menggunakan perintah php artisan test. Test suite yang dieksekusi mencakup dua tingkatan pengujian:
a. Unit Test (Tests\Unit\ExampleTest): Berfungsi memverifikasi logika mendasar dengan assertion bahwa nilai logika benar bernilai benar (that true is true).b. Feature Test (Tests\Feature\ExampleTest): Berfungsi memvalidasi fungsionalitas rute web utama ('/'), memastikan bahwa server merespons dengan kode status HTTP 200 OK serta memastikan halaman memuat teks kunci 'Evolusi Pemrograman Lanjut' dan 'Project Dashboard'.

Keberhasilan pengujian lokal ini menjadi fondasi awal (baseline) yang membuktikan bahwa aplikasi berada dalam status stabil dan siap diintegrasikan ke dalam sistem otomasi Continuous Integration.
2. Perancangan dan Implementasi Workflow CI/CD Empat Tahap (.github/workflows/ci.yml)
Untuk menerapkan prinsip Continuous Integration dan Continuous Deployment secara nyata, dibuat berkas konfigurasi workflow GitHub Actions pada direktori .github/workflows/ci.yml. Sesuai instruksi penugasan, pipeline dirancang memiliki empat tahapan pekerjaan yang berurutan (sequential multi-stage pipeline), yaitu: build → test → staging → production. Ketergantungan dan urutan eksekusi antar-job dikendalikan secara deterministik menggunakan direktif 'needs:'. Workflow ini dikonfigurasi agar terpicu secara otomatis pada setiap event push ke cabang 'main', 'dev', dan 'feature/**', serta event pull_request ke cabang 'main' dan 'dev'.
A. Konfigurasi Job Build
Job build bertindak sebagai gerbang awal dalam pipeline yang berjalan pada pelari virtual Ubuntu (runs-on: ubuntu-latest). Tujuan utama dari job ini adalah memastikan kode sumber dapat diambil secara bersih dan seluruh pustaka dependensi pihak ketiga dapat dipasang tanpa menimbulkan konflik dependensi. Langkah-langkah yang dieksekusi meliputi:1. Checkout repository: Mengunduh salinan repositori ke lingkungan runner menggunakan actions/checkout@v4.2. Setup PHP: Mengonfigurasi lingkungan runtime PHP versi 8.4 menggunakan action shivammathur/setup-php@v2 lengkap dengan ekstensi yang disyaratkan (mbstring, dom, fileinfo, sqlite3).
3. Install Composer dependencies: Menjalankan perintah 'composer install --no-interaction --prefer-dist --optimize-autoloader' guna menginstal seluruh paket dependensi secara optimal.
Gambar 3. Konfigurasi job build pada berkas .github/workflows/ci.yml.
B. Konfigurasi Job Test
Job test dirancang untuk menjalankan pengujian otomatis di lingkungan cloud GitHub Actions. Job ini didefinisikan dengan klausul dependensi 'needs: build', yang artinya job test hanya akan dieksekusi apabila job build berhasil diselesaikan tanpa galat. Selain melakukan checkout kode dan penyusunan dependensi, job ini mereplikasi lingkungan aplikasi secara terisolasi dengan tahapan:1. Prepare environment: Menyalin berkas konfigurasi sampel (.env.example) menjadi berkas konfigurasi aktif (.env) melalui perintah 'cp .env.example .env'.2. Generate application key: Menghasilkan kunci enkripsi unik aplikasi melalui perintah 'php artisan key:generate'.3. Run tests: Mengeksekusi rangkaian pengujian fungsional dan unit otomatis menggunakan perintah 'php artisan test'.
Gambar 4. Konfigurasi job test dengan dependensi needs: build pada berkas ci.yml.
C. Konfigurasi Job Staging
Setelah pengujian otomatis pada job test berhasil, alur pipeline berlanjut ke job staging yang memiliki dependensi 'needs: test'. Job staging merepresentasikan lingkungan prapengujian (pre-production replica) yang digunakan oleh tim pengembang dan penjamin mutu (QA) untuk memvalidasi build sebelum dirilis ke publik. Karena pada penugasan ini belum dihubungkan ke server fisik, proses deployment ke staging disimulasikan melalui perintah shell pencetakan log:run: echo "Deploying application to staging...".
Gambar 5. Konfigurasi job staging dengan dependensi needs: test pada berkas ci.yml.
D. Konfigurasi Job Production
Tahap puncak dalam pipeline adalah job production yang dirangkai menggunakan dependensi 'needs: staging'. Job production ini diberikan perlindungan berlapis guna menjamin keamanan dan stabilitas sistem:
Pembatasan Cabang (Branch Guard): Diterapkan menggunakan ekspresi kondisional 'if: github.ref == \'refs/heads/main\''. Klausul ini mengunci eksekusi job production agar hanya dapat berjalan apabila kode berasal dari branch utama (main). Commit yang didorong ke branch fitur secara otomatis akan melewati (skip) job ini.
Otorisasi Lingkungan (Environment Protection): Diterapkan melalui penugasan 'environment: production'. Penugasan ini mengaktifkan kebijakan proteksi rilis pada GitHub di mana proses deployment wajib menunggu peninjauan dan persetujuan manual (Required Reviewer).
Eksekusi 7 Langkah Deployment: Seluruh instruksi pemeliharaan dan pembaruan aplikasi dieksekusi secara urut menggunakan perintah echo.
Gambar 6. Konfigurasi job production dengan kondisi if branch main dan proteksi environment production.
3. Implementasi Skrip Otomasi Deployment Server (deploy.sh) dan Pemetaannya pada CI/CD
Dalam implementasi DevOps standar industri, pembaruan aplikasi pada server produksi dijalankan menggunakan skrip otomasi shell. Oleh karena itu, dibuat berkas skrip bernama deploy.sh pada direktori utama repositori. Skrip ini diawali dengan shebang '#!/usr/bin/env bash' dan direktif keselamatan 'set -e'. Direktif 'set -e' (errexit) memiliki fungsi krusial untuk memerintahkan shell agar segera menghentikan eksekusi skrip seketika jika terdapat perintah yang menghasilkan kode keluar bukan nol (terjadi galat/error). Hal ini mencegah terjadinya partial deployment yang berpotensi merusak integritas sistem dan basis data di lingkungan produksi.
Skrip deploy.sh mengimplementasikan 7 langkah deployment aplikasi Laravel secara terstruktur:1. php artisan down --retry=60: Mengaktifkan mode pemeliharaan (maintenance mode) dengan parameter retry 60 detik agar pengguna mendapatkan respons yang bersahabat saat server diperbarui.2. git pull origin main: Menarik kode sumber versi terbaru dari cabang utama repositori remote.3. composer install --no-dev --optimize-autoloader: Menginstal paket dependensi murni untuk produksi tanpa paket pengujian/pengembangan guna efisiensi memori dan optimasi kecepatan akses autoloader.4. php artisan migrate --force: Menjalankan migrasi skema database dengan flag --force untuk menghindari prompt konfirmasi interaktif pada runner non-TTY.5. Pembangunan Cache Kinerja: Mengeksekusi 'php artisan config:cache', 'php artisan route:cache', dan 'php artisan view:cache' untuk menyatukan dan mengompilasi konfigurasi, rute, dan tampilan Blade ke dalam cache statis demi performa maksimal.6. php artisan queue:restart: Merestart proses background worker queue agar mengeksekusi logika kode terbaru.7. php artisan up: Mematikan status pemeliharaan dan membuka kembali layanan aplikasi kepada pengguna.
Gambar 7. Berkas skrip deploy.sh lengkap dengan deklarasi set -e dan 7 langkah pemeliharaan deployment.
Untuk memenuhi ketentuan bahwa proses deployment belum dihubungkan langsung ke server fisik, ketujuh langkah dari skrip deploy.sh dipetakan secara identik ke dalam job production pada berkas .github/workflows/ci.yml menggunakan perintah pencetakan 'echo'. Pendekatan ini berfungsi sebagai simulasi dry-run yang memvalidasi bahwa seluruh tahapan skrip deployment terpanggil secara presisi dan terorkestrasi dengan baik oleh GitHub Actions runner.
Gambar 8. Implementasi tujuh tahapan deployment berbasis perintah echo pada job production di ci.yml.
4. Konfigurasi Keamanan Deployment ke Environment Production (Deployment Protection Rules)
Aspek tata kelola dan keamanan rilis diatur melalui konfigurasi Environment pada GitHub Actions. Melalui menu Settings &gt; Environments pada repositori, dibuat sebuah environment bernama 'production'. Pada environment ini, dikonfigurasi Deployment Protection Rules yang mewajibkan adanya peninjauan manual (Required reviewers) oleh akun pemilik repositori ('EricoAli'). Aturan ini menjadi gerbang persetujuan (approval gate) sehingga pipeline tidak dapat secara otomatis menyebarkan perubahan ke sistem produksi tanpa otorisasi formal.
Selain itu, dikonfigurasi batasan cabang deployment (Deployment branches and tags) dengan menetapkan 'Selected branches and tags' dan mendaftarkan hanya cabang 'main' ('Currently applies to 1 branch'). Kebijakan ini memastikan bahwa tidak ada cabang lain (seperti cabang eksperimen atau cabang fitur) yang dapat memicu atau mengakses rahasia (secrets) lingkungan produksi.
Gambar 9. Konfigurasi Deployment Protection Rules pada environment production dengan Required Reviewer dan proteksi branch main.
5. Pengujian, Pembuktian, dan Verifikasi Pipeline CI/CD
Untuk memverifikasi bahwa seluruh aturan logika pipeline, pembatasan cabang, dan perlindungan pengujian berjalan sesuai rancangan, dilakukan serangkaian skenario pengujian praktis sebagai berikut:
A. Skenario 1: Eksekusi Pipeline pada Feature Branch (Branch-based Gating)
Pengujian pertama dilakukan dengan mendorong perubahan kode pada branch pengembangan fitur bernama 'feature/ci-pipeline' (Commit 620e124). Berdasarkan aturan yang dirancang, branch fitur ditujukan untuk pengembangan kode dan pengujian awal, sehingga tidak boleh mengeksekusi deployment production. Diagram visual hasil eksekusi pada Gambar 10 memperlihatkan bahwa job Build (18 detik), Test (18 detik), dan Staging (4 detik) berhasil diselesaikan dengan indikator centang hijau. Sebaliknya, job Production berstatus dilewati (Skipped, durasi 0 detik dengan lambang abu-abu tercoret). Hasil ini membuktikan bahwa filter kondisional 'if: github.ref == \'refs/heads/main\'' berhasil mengevaluasi nilai false dan secara efektif mengabaikan job production pada branch fitur, sementara fungsi continuous integration tetap berjalan normal.
Gambar 10. Diagram visual eksekusi pipeline pada branch fitur: Build, Test, Staging sukses, Production berstatus skipped.
B. Skenario 2: Ketahanan Pipeline terhadap Kegagalan Automated Test (Fail-Fast)
Pengujian kedua dirancang untuk menguji keandalan prinsip Fail-Fast pada Continuous Integration. Pada cabang fitur, dibuat commit khusus (Commit 5d125af dengan pesan 'test: verify pipeline fails on failing test') di mana kode pengujian pada tests/Feature/ExampleTest.php sengaja digagalkan dengan mengubah ekspektasi status HTTP dari 200 menjadi 500 ($response-&gt;assertStatus(500)).
Ketika commit tersebut didorong ke GitHub, job Build berhasil diselesaikan, namun alur pipeline langsung terhenti pada job Test dengan indikator silang merah (Failed). Log konsol pada Gambar 11 mencatat galat secara terperinci:'FAILED Tests\Feature\ExampleTest &gt; dashboard page is accessible''Expected response status code [500] but received 200. Failed asserting that 200 is identical to 500.'Proses pengujian keluar dengan 'exit code 1'. Karena job Staging dan Production bergantung pada 'needs: test', kedua job berikutnya secara otomatis dibatalkan dan tidak pernah dieksekusi. Bukti ini mendemonstrasikan bahwa sistem CI berhasil mencegah penyebaran kode yang cacat atau bermasalah ke lingkungan selanjutnya.
Gambar 11. Log kegagalan eksekusi job test pada GitHub Actions akibat kegagalan assertion HTTP status.

D. Skenario 4: Verifikasi Deployment Protection Gate pada Branch Utama (main)
Setelah kode dipastikan lulus uji dan diperbaiki, commit digabungkan dan didorong ke branch utama 'main'. Pada eksekusi ini, diagram alir GitHub Actions menunjukkan bahwa job Build (20 detik), Test (18 detik), dan Staging (3 detik) berhasil dieksekusi dengan sempurna (centang hijau). Berbeda dengan eksekusi pada branch fitur, job Production tidak dilewati melainkan aktif dan berada dalam status 'Waiting' (ditandai dengan ikon jam oranye dan status 'production waiting for review').

Kondisi ini secara nyata membuktikan keberhasilan konfigurasi Deployment Protection Rules, di mana sistem menahan proses deployment ke lingkungan produksi hingga reviewer yang berwenang memberikan persetujuan.
Gambar 13. Diagram alir pipeline pada branch main yang tertahan pada status Waiting for Review sebelum eksekusi deployment production.

6. Kesimpulan
Berdasarkan pelaksanaan praktikum Manajemen GitHub &amp; Prinsip Continuous Integration pada modul ini, dapat ditarik beberapa kesimpulan utama sebagai berikut:
1. Berhasil membangun dan mengintegrasikan aplikasi web Laravel 13 dengan sistem otomasi CI/CD modern menggunakan GitHub Actions. Pipeline berhasil mengorkestrasi empat tahapan kerja utama (build, test, staging, production) secara berurutan menggunakan klausul 'needs:'.2. Penerapan pengujian otomatis (automated testing) menggunakan 'php artisan test' di lingkungan isolated runner terbukti mampu mewujudkan prinsip Fail-Fast. Saat terjadi kegagalan test suite, pipeline secara seketika memutus alur eksekusi, sehingga mencegah kode yang cacat (buggy) merambat ke tahap rilis lebih lanjut.3. Penerapan strategi isolasi cabang dan perlindungan lingkungan (branch-based gating and environment protection rules) berhasil diimplementasikan secara efektif. Eksekusi dari branch pengembangan fitur dibatasi hanya sampai tahap staging (production skipped), sedangkan eksekusi pada branch utama (main) mewajibkan adanya otorisasi manual dari Required Reviewer sebelum deployment produksi dapat dijalankan.4. Perancangan skrip deploy.sh yang dilengkapi dengan direktif 'set -e' dan pemetaannya ke dalam perintah echo pada workflow berhasil mensimulasikan tujuh langkah standar pemeliharaan server Laravel (maintenance mode, penarikan kode, resolusi dependensi produksi, migrasi database, caching performa, queue restart, dan pembukaan aplikasi kembali) secara deterministik dan aman.
